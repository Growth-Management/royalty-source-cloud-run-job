# PODデータ加工仕様

## 目的

手順書「7 PODデータの加工」を、Cloud Run JobとBigQueryで再現する。

MS AccessのPOD販売報告テーブルを置換し、初期累積履歴と月次差分を同じAccess互換形式へ統合する。

## 確定した入力構成

### 初期移行正本

- 原本: MS Accessへ2026年2月分まで取り込んだ後の`⑤POD販売報告データ`
- BigQuery既存正本: `ice-qb.ice_qb_source_p1.pod_sales_summary`
- BigQuery既存正本の行数: 3,392行
- 対象期間: 2014年3月から2026年2月
- 取込回数: 一度だけ
- 用途: `royalty_*`側のBigQuery初期履歴

`ice_qb_source_p1.pod_sales_summary`は旧MS AccessのA7「⑤POD販売報告データ」をBigQueryへ取り込んだ既存テーブルであり、2026年2月の19行も保持している。初期移行時はこれを正本として扱う。

`ice_qb_source_p1`はUS、`royalty_*`は`asia-northeast1`にあるため、SQLで直接JOINしない。一度だけAPI/エクスポート・ロード等でUSからasia-northeast1へ履歴シードを移送し、その後はasia-northeast1内で処理する。

`【取込み用】202601_AmazonPOD販売実績(ICE).xlsx`は初期累積正本ではない。加工過程・月次シート構造の確認資料として扱い、2026年2月の19行をこのファイルから推測生成しない。

### 月次差分

2026年3月以降は次の2系統を取り込む。

1. 従来Amazon POD月次データ
2. `【PF】販売レポート_*.csv`

2026年2月のAccess結果では、従来Amazon POD由来4行とPF販売レポート由来15行が統合されていた。2026年2月は新月次処理の入力月ではなく、初期履歴と月次差分の境界・回帰テスト月として扱う。

## 推奨テーブル

### STAGING

- `staging_pod_access_history`
- `staging_amazon_pod_monthly`
- `staging_pf_sales_report`

### RAW

- `raw_pod_access_history`
- `raw_amazon_pod_monthly`
- `raw_pf_sales_report`

STAGINGとRAWでは業務計算を行わず、元文字列と次のメタデータを保持する。

- `source_file_id`
- `source_file_name`
- `source_sheet_name`
- `row_number`
- `target_month`
- `loaded_at`
- `run_id`（監査ログとの関連付けで保持可能にする）

### SOURCE

- `source_pod_sales_report`

MS AccessのPOD販売報告テーブル相当の共通形式を生成する。

## Access互換列

| Access列 | 内容 |
|---|---|
| 発行社 | 原則 `ICE` |
| プロダクトコード | 入力値または商品マスタ補完 |
| ISBN | 入力値または商品マスタ補完。STRINGで保持 |
| タイトル | 入力値または商品マスタ正式タイトル |
| 単価 | 税別販売価格 |
| 掛率 | 従来Amazon POD入力値を保持。PFは既存Access結果との比較で確定 |
| 冊数 | 販売数 |
| 正味金額 | 売上金額（税別） |
| 消費税 | 原則0 |
| 売上金額 | 売上金額（税別） |
| 製造原価 | 下記変換規則 |
| 15 | 固定値 `1.5` |
| 108 | 固定値 `108` |
| 頁数 | 入力値または商品マスタ補完 |
| DL年月 | 原則、販売対象月の前月 `YYYYMM` |
| 年月 | 販売対象月 `YYYYMM` |

## PF販売レポート変換規則

| Access列 | PF CSV列・計算 |
|---|---|
| 発行社 | `ICE` |
| ISBN | `ISBN`。指数表記や欠損時は商品マスタから補完 |
| タイトル | `書籍名`または商品マスタ正式タイトル |
| 単価 | `販売価格（税別）` |
| 冊数 | `販売数` |
| 正味金額 | `売上金額（税別）` |
| 消費税 | `0` |
| 売上金額 | `売上金額（税別）` |
| 製造原価 | `販売手数料（税別） + 印刷費（税別）` |
| DL年月 | 販売月の前月 |
| 年月 | 販売月 |

次の関係を品質チェックする。

```text
支払額 = 売上金額 - 製造原価
       = 売上金額 - 販売手数料 - 印刷費
```

`販売数 = 0`の行はAccess取込対象から除外する。ただしRAWには保持する。

## 従来Amazon POD月次データ

従来形式は、既存の月次POD販売実績の列をAccess互換列へマッピングする。

- 転記用シートと元月次シートを同時に取り込まない
- `請求書`など販売明細以外のシートを除外する
- 月次シートから販売冊数が0でない行をSOURCE化する
- プロダクトコード、ISBNはSTRINGで保持する
- 同一対象月を再実行しても、最新ファイル・最新ロード行だけをSOURCE化して重複させない

## 初期移行方式

初回のみ`ice_qb_source_p1.pod_sales_summary`の3,392行をUSからasia-northeast1側の履歴シードへ移送する。

移送後は、対象期間2014年3月から2026年2月の件数・数量・金額を正本と照合する。初期移行済みフラグまたは監査レコードによって二重投入を防止する。

## 月次方式

通常月次処理は2026年3月以降を対象とし、対象月単位で冪等に処理する。

1. 対象月の従来Amazon POD月次データをRAWへロード
2. 対象月のPF販売レポートをRAWへロード
3. 両入力をAccess互換形式へ変換
4. 対象月のSOURCEを置換
5. 品質チェックを実行

SOURCEは対象月単位のDELETE+INSERT、またはCREATE OR REPLACE相当で再実行時に重複しないこと。RAWを累積保持する場合も、SOURCE生成時は最新ファイル・最新ロード行だけを採用する。

## 2026年2月再現テスト

2026年2月を回帰テストの基準月とする。正解値は`ice_qb_source_p1.pod_sales_summary`の`year_month = 202602`と一致する。

| 指標 | 期待値 |
|---|---:|
| 行数 | 19 |
| 冊数合計 | 38 |
| 売上金額合計 | 51,138円 |
| 製造原価合計 | 37,027円 |
| 従来Amazon POD由来行数 | 4 |
| PF販売レポート由来行数 | 15 |

PF販売レポートの販売数非0行15件は、Access結果と販売数、売上金額、製造原価が一致すること。

## 品質チェック

最低限、次を監査テーブルへ記録する。

- 対象月NULL・不一致
- 販売数、売上金額、販売手数料、印刷費、製造原価の型変換失敗
- PF支払額計算不一致
- 販売数0行がSOURCEへ混入
- 商品マスタ未一致
- プロダクトコード未補完
- ISBN未補完または不正桁
- 業務キー重複
- 対象月SOURCE 0件
- 2026年2月の期待件数・数量・金額差分

集計値の差異チェックでは、`error_count`に差額・差冊数を入れない。チェックが不一致なら`error_count = 1`とし、期待値・実績値・差分は`sample_json`等の詳細へ保持する。

## 実装上の注意

- PF CSVはCP932、UTF-8 BOMなどを順に判定して読む。
- ISBN、プロダクトコード、書籍IDは数値型にしない。
- 元ファイルの列はRAWで欠落させない。
- 商品マスタ・著者条件は既存BigQuery参照マスタを利用し、月次処理で重複生成しない。
- 初期履歴と月次差分の境界は2026年2月末とし、通常月次処理は2026年3月から開始する。
